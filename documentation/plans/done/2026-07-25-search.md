## Step 0: real-NAS probe (read only) -- DONE, findings below

Ran a throwaway `core/photoscore/examples/probe_search.rs` against the real
NAS (reusing the saved session's sid, no OTP needed), then deleted it per
the brief (never committed). Confirmed facts:

- `SYNO.API.Info` advertises `SYNO.Foto.Search.Search` (v1-7) and
  `SYNO.Foto.Search.Filter` (v1-4), matching the brief.
- The real method is **`list_item`**, not `list` or `search`. Both of
  those guesses returned error 103 (no such method) even though the API
  itself exists (control: a bogus api name returns error 102 "no such
  API", a different code, proving `list`/`search` are rejected at the
  method level on a real API).
- The real keyword param is **`keyword`**, not `query`. Confirmed with two
  controls: `keyword=zzzznosuchthing123` (a value that cannot match
  anything) returns a clean empty list, proving `keyword` genuinely
  filters; sending `query=food` instead of `keyword` returns error 100
  ("invalid parameter"), proving DSM validates the param set and `query`
  is not a silently-accepted alias.
- Results are **flat**, not grouped: `{"data":{"list":[...]}}`, the same
  envelope shape as `Browse.Item`. No people/places/tags sections.
- `additional=["thumbnail","resolution"]` is honored identically to
  `Browse.Item`: `cache_key`/`unit_id` under `additional.thumbnail`,
  `width`/`height` under `additional.resolution`. The existing `RawItem`
  decoder in `browse.rs` applies to search rows without modification.
- Item `type` on search results includes `"live"` (Live Photos), a value
  never seen from `Browse.Item` on this account. Decodes as
  `MediaKind::Unknown` per the existing fail-open convention; not a new
  problem, just a new observed value.
- `offset`/`limit` are respected (a `limit=10` request against a broader
  keyword returned exactly as many as matched, capped at 10).
- `SYNO.Foto.Search.Filter` `method=list` works and returns real facets
  (camera, geocoding tree, iso, time buckets, folder_filter, etc.) on this
  account. Confirmed present but data-heavy; deferred per the brief's
  "ship plain keyword search, log facets as a follow-up" clause.

## Step 1: synology-api search()

Add `search()` to `browse.rs` (or a small sibling module): same
`get_body`/`decode_one`/`ItemList` pattern as `list_items`, method
`list_item`, param `keyword`, `additional=["thumbnail","resolution"]`,
X-SYNO-TOKEN header. Personal space only (`SYNO.Foto.Search.Search`; no
`FotoTeam` equivalent probed or in scope). Reuses `RawItem`/`Asset`
end to end -- no new model needed.

Tests: mockito -- token header sent, `keyword` param sent, tolerant
per-element decode (a malformed row skipped, not fatal), empty result
list decodes cleanly, `unit_id`/`cache_key` mapped the same way as
`list_items`.

## Step 4: app search field

- Toolbar search field (SwiftUI `.searchable` on the split view, bound to
  a debounced query string).
- `WindowedDataSource` gains a third `FetchSource` case (`.search(String)`)
  alongside `.space`/`.collection`, windowed the same way a discovery
  collection is (live fetch, no local index, `isReady`/`totalCount`
  estimated from page size the same way).
- Empty query clears back to whatever the sidebar selection currently
  routes to. Non-empty query with zero results shows a clean "No results
  for <query>" empty state (new small view, same visual language as
  `EmptyLibraryView`/`DiscoveryGridEmptyView`).
- Debounce (roughly 300ms) before firing the search, so typing does not
  spam the NAS on every keystroke.
